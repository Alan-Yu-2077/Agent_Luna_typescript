# v0.28.0 — First-run onboarding

> **Status: PLANNED.** Initiative: Desktop first-run & pet ergonomics (Order 1, version 1/3). Risk: **Medium**.
> Depends: nothing. Flag: none (gated by first-run detection; a `LUNA_SKIP_ONBOARDING=1` escape hatch for dev).

## Goal

Replace the "edit `luna.env` by hand, then relaunch" first-run chore with a guided setup screen. On a
fresh install the desktop shell shows a small form (API base URL + key, optional model / weather
location), writes the values to `userData/luna.env`, and **restarts the sidecar in place** so the very
next chat turn works — no dotfile, no manual full-app relaunch. Keys are written by a shell-only IPC and
never touch the settings wire.

## What ships

**Shell (`packages/desktop`):**
- `src/supervisor.ts` — add **`restart()`** to `type Supervisor` (`supervisor.ts:26`): `stop()` the child
  (disarm the crash-restart latch), then re-`start()` with a freshly-computed env. Injectable-`spawnFn`
  friendly (the existing test seam). This is the missing capability today (`start`/`stop` only).
- `src/onboarding.ts` (NEW) — `needsOnboarding(userEnv): boolean` = the real key is absent/placeholder
  (mirrors the `sk-not-configured` sentinel logic in `sidecarEnv`, `main.ts:83`); `writeOnboarding(p, fields)`
  = merge the submitted fields into `luna.env` **preserving existing lines/comments** (extend `envfile.ts`'s
  parse with a line-preserving write, NOT a template overwrite — a re-run must not clobber other keys).
  Pure + unit-testable (no Electron import).
- `src/main.ts` — on boot, after `ensureUserConfig`, if `needsOnboarding(userEnv)` and not `SMOKE`/`LUNA_SKIP_ONBOARDING`:
  load the **setup route** instead of the app (`?setup=1`), skip spawning the sidecar until saved. New
  `ipcMain.handle('luna:onboarding-submit', …)` (handle, not on — it returns a result): validate fields,
  `writeOnboarding`, recompute `sidecarEnv`, `supervisor.restart()` (or start if not yet started), wait
  `waitForPort`, then tell the renderer to navigate to the app. **Never** returns the key back.
- `src/preload.ts` — `contextBridge` gains `lunaSetup.submit(fields) → Promise<{ok, error?}>` and
  `lunaSetup.isFirstRun() → boolean`. Same shape as the existing `lunaPet` bridge.
- Remove the blocking first-run `dialog.showMessageBoxSync` (`main.ts:59`) — the setup screen replaces it.
  Keep writing the `ENV_TEMPLATE` so `luna.env` still documents every field for power users.

**Web (`packages/web`):**
- `src/ui/setupView.ts` (NEW) — a self-contained setup form (base URL, API key [type=password], model
  [optional, defaults to the built-in], weather location [optional]) matching `theme.css` styling. Shown when
  `?setup=1` is present (or the `lunaSetup` bridge reports first-run); posts via `lunaSetup.submit`, shows a
  spinner + inline error on failure (bad key → the sidecar won't answer → surface "couldn't reach the model,
  check the URL/key"). On success the shell navigates to the app.
- `src/app.ts` — early branch: if `?setup=1`, mount `setupView` and **do not** open the WS / build the model.

**No wire-contract change.** `settings.set`/`settings.state` are untouched — keys deliberately do NOT go
through them (the v0.27.1 registry is secret-free by construction). No SQLite/schema change.

## Tests

- `onboarding.test.ts`: `needsOnboarding` true on empty/placeholder key, false on a real key; `writeOnboarding`
  merges into existing `luna.env` **without dropping unrelated lines/comments**, updates an existing key in
  place, appends a missing one, and round-trips through `parseEnvFile`.
- `supervisor.test.ts` (+cases): `restart()` kills the old child then spawns a new one with the new env
  (assert via the injectable `spawnFn` that the second spawn sees the updated key); `restart()` re-arms the
  crash-restart budget; `stop()` after `restart()` still disarms.
- Secret-safety assertion: the `luna:onboarding-submit` handler's return value shape contains **no key field**
  (unit-test the handler payload).
- Full suite green; `tsc` ×4 clean.

## What this version explicitly does NOT include

- No editing of keys AFTER first run through the UI (that's a "re-run setup" affordance — a later polish;
  power users still edit `luna.env` + restart). v0.28.0 is the first-run path only.
- No secret storage in the OS keychain (stays a file in `userData`, per the Frontend LD). Keychain is a
  future hardening, not this slice.
- No onboarding in the browser/dev build (`.env` there is the developer's own; the setup screen is desktop-only,
  gated by the `lunaSetup` bridge's presence).

## Risk

- **Applying keys without a full relaunch** hinges on `supervisor.restart()` cleanly re-spawning against the
  new env. Mitigation: the injectable `spawnFn` test proves the second spawn sees the new key; `waitForPort`
  gates the navigate-to-app so a still-booting sidecar can't show a dead chat.
- **Key leak.** Mitigation: the key rides one IPC direction (renderer→main), is written only to `luna.env`,
  and the handler never echoes it; a test asserts the response carries no key. It never enters `settings.*`.
- **Clobbering a hand-edited `luna.env`.** Mitigation: `writeOnboarding` is line-preserving merge, not a
  template rewrite; tested against a file with pre-existing unrelated keys/comments.

## Acceptance criteria

- [ ] Fresh `userData` → app opens on the setup screen, not the chat.
- [ ] Entering a valid base URL + key + Save → `luna.env` gains the keys, the sidecar (re)starts, `waitForPort`
      succeeds, the window navigates to the chat, and a turn works — no manual file edit or app relaunch.
- [ ] A bad key → inline "couldn't reach the model" error on the setup screen; no navigate.
- [ ] Re-running against an existing `luna.env` with other keys set preserves them.
- [ ] The submitted key never appears in any IPC response, `settings.state`, or trace.
- [ ] `LUNA_SKIP_ONBOARDING=1` (and `LUNA_SMOKE=1`) bypass the gate.

## Notes for v0.28.1 (don't foreclose)

`setupView.ts` and `settingsView.ts` (v0.27.1) should share the same visual primitives (`theme.css`
`.setting-row`/`.setting-input`) so a future "edit setup later" panel can reuse either. `restart()` on the
supervisor is generally useful (a future "apply restart-required setting live" could call it) — keep it env-agnostic
(recompute env at call time), not onboarding-specific.
